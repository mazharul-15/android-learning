# Android Activity Lifecycle with Kotlin

## 1. What is an Activity?

An **Activity** is an Android application component that represents a screen or entry point for user interaction.

The Activity Lifecycle describes the states an Activity goes through from creation to destruction.

Main lifecycle callbacks:

1. `onCreate()`
2. `onStart()`
3. `onResume()`
4. `onPause()`
5. `onStop()`
6. `onDestroy()`

An Activity can also receive `onRestart()` when returning from the stopped state.

---

## 2. Basic Lifecycle Flow

```text
onCreate()
    ↓
onStart()
    ↓
onResume()
    ↓
  User leaves / loses focus
    ↓
onPause()
    ↓
onStop()
    ↓
  User returns
    ↓
onRestart()
    ↓
onStart()
    ↓
onResume()
```

If the Activity is finished or destroyed:

```text
onPause() → onStop() → onDestroy()
```

---

## 3. `onCreate()`

`onCreate()` is called when the system first creates the Activity.

Use it for basic startup work that happens once for that Activity instance:

- Set the layout with `setContentView()`
- Initialize UI components
- Set up View Binding
- Initialize a ViewModel
- Set listeners
- Restore appropriate saved state

### Kotlin

```kotlin
class MainActivity : AppCompatActivity() {

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        setContentView(R.layout.activity_main)

        // Initialize UI and other components
    }
}
```

The Activity then moves toward the Started and Resumed states.

---

## 4. `onStart()`

`onStart()` is called when the Activity becomes visible to the user.

Good uses include work required while the Activity is visible.

```kotlin
override fun onStart() {
    super.onStart()

    Log.d("Lifecycle", "onStart")
}
```

---

## 5. `onResume()`

`onResume()` is called when the Activity comes to the foreground and can interact with the user.

Good uses:

- Resume animations
- Start foreground-only functionality
- Resume a camera preview
- Refresh resources that were released in `onPause()`

```kotlin
override fun onResume() {
    super.onResume()

    Log.d("Lifecycle", "onResume")
}
```

An Activity normally remains Resumed until something takes focus away from it.

---

## 6. `onPause()`

`onPause()` is called when the Activity loses foreground focus.

Important: a Paused Activity may still be visible, particularly in multi-window mode.

Good uses:

- Pause short-lived foreground work
- Release resources that are not needed while paused
- Pause camera preview or similar foreground-only functionality

```kotlin
override fun onPause() {
    super.onPause()

    Log.d("Lifecycle", "onPause")
}
```

### Important

Keep `onPause()` lightweight.

Do **not** use it for heavy database operations, network requests, or important save operations because the callback is expected to complete quickly.

---

## 7. `onStop()`

`onStop()` is called when the Activity is no longer visible.

Good uses:

- Stop visibility-dependent work
- Release resources not needed while the Activity is hidden
- Perform relatively CPU-intensive shutdown work when appropriate
- Save persistent information when no better opportunity exists

```kotlin
override fun onStop() {
    super.onStop()

    Log.d("Lifecycle", "onStop")
}
```

---

## 8. `onRestart()`

`onRestart()` is called when an Activity that was previously stopped is about to start again.

Typical sequence:

```text
onStop()
   ↓
onRestart()
   ↓
onStart()
   ↓
onResume()
```

Example:

```kotlin
override fun onRestart() {
    super.onRestart()

    Log.d("Lifecycle", "onRestart")
}
```

It is less commonly overridden than the other callbacks.

---

## 9. `onDestroy()`

`onDestroy()` is called before the Activity is destroyed.

This can happen when:

- The Activity is finishing
- `finish()` is called
- A configuration change occurs, such as rotation
- The system temporarily destroys the Activity for a configuration change

```kotlin
override fun onDestroy() {
    super.onDestroy()

    Log.d("Lifecycle", "onDestroy")
}
```

Do not rely on `onDestroy()` as the only place to save important application data.

---

# 10. Complete Kotlin Lifecycle Example

```kotlin
package com.example.lifecycleapp

import android.os.Bundle
import android.util.Log
import androidx.appcompat.app.AppCompatActivity

class MainActivity : AppCompatActivity() {

    private val tag = "ActivityLifecycle"

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)

        Log.d(tag, "onCreate")
    }

    override fun onStart() {
        super.onStart()
        Log.d(tag, "onStart")
    }

    override fun onResume() {
        super.onResume()
        Log.d(tag, "onResume")
    }

    override fun onPause() {
        super.onPause()
        Log.d(tag, "onPause")
    }

    override fun onStop() {
        super.onStop()
        Log.d(tag, "onStop")
    }

    override fun onRestart() {
        super.onRestart()
        Log.d(tag, "onRestart")
    }

    override fun onDestroy() {
        super.onDestroy()
        Log.d(tag, "onDestroy")
    }
}
```

# 11. Activity Lifecycle States

| State | Meaning | Common callback |
|---|---|---|
| Created | Activity has been created | `onCreate()` |
| Started | Activity is visible | `onStart()` |
| Resumed | Activity is in foreground and interactive | `onResume()` |
| Paused | Activity has lost foreground focus | `onPause()` |
| Stopped | Activity is no longer visible | `onStop()` |
| Destroyed | Activity instance is being destroyed | `onDestroy()` |

# 12. Common Scenarios

## App starts

```text
onCreate()
onStart()
onResume()
```

## User opens another full-screen Activity

```text
onPause()
onStop()
```

When the user returns:

```text
onRestart()
onStart()
onResume()
```

## Activity is finished

```text
onPause()
onStop()
onDestroy()
```

## Screen rotation

A configuration change can destroy the current Activity and create a new Activity instance.

Typical flow:

```text
Old Activity:
onPause()
onStop()
onDestroy()

New Activity:
onCreate()
onStart()
onResume()
```

Use appropriate state-management mechanisms so important UI state can survive recreation.

# 13. ViewModel and Activity Lifecycle

A `ViewModel` is useful for holding UI-related state across configuration changes such as screen rotation.

```kotlin
class MainViewModel : ViewModel() {

    var counter = 0
}
```

Activity:

```kotlin
class MainActivity : AppCompatActivity() {

    private val viewModel: MainViewModel by viewModels()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        setContentView(R.layout.activity_main)

        viewModel.counter++
    }
}
```

A ViewModel associated with the Activity can survive configuration-change recreation.

---

# 14. Saving UI State

For small, transient UI state, Android provides saved-state mechanisms.

For Jetpack Compose, `rememberSaveable` can preserve lightweight UI state across Activity recreation.

Example:

```kotlin
@Composable
fun SearchScreen() {

    var query by rememberSaveable {
        mutableStateOf("")
    }

    TextField(
        value = query,
        onValueChange = { query = it }
    )
}
```

For more complex screen state, use a suitable combination of `ViewModel`, saved state, and persistent storage.

---

# 15. Lifecycle-Aware Components

AndroidX provides lifecycle-aware APIs that allow components to react to lifecycle changes.

Example:

```kotlin
class MyLifecycleObserver : DefaultLifecycleObserver {

    override fun onStart(owner: LifecycleOwner) {
        super.onStart(owner)

        Log.d("Lifecycle", "Activity started")
    }

    override fun onStop(owner: LifecycleOwner) {
        super.onStop(owner)

        Log.d("Lifecycle", "Activity stopped")
    }
}
```

Register the observer:

```kotlin
class MainActivity : AppCompatActivity() {

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        lifecycle.addObserver(MyLifecycleObserver())
    }
}
```

Lifecycle-aware components help keep lifecycle-dependent logic organized and reusable.

---

# 16. Jetpack Compose and Lifecycle

For modern Compose applications, avoid putting business logic or manual lifecycle observation directly into Activity callbacks when lifecycle-aware Compose APIs are more appropriate.

For example, `collectAsStateWithLifecycle()` can collect a Flow from a ViewModel according to the UI lifecycle.

```kotlin
@Composable
fun UserScreen(viewModel: UserViewModel) {

    val uiState by viewModel.uiState
        .collectAsStateWithLifecycle()

    // Render UI using uiState
}
```

This helps prevent unnecessary work while the UI is not in an appropriate lifecycle state.

# 17. Activity A Starts Activity B

When Activity A starts Activity B, the lifecycle transitions overlap.

A typical sequence is:

```text
Activity A: onPause()

Activity B:
    onCreate()
    onStart()
    onResume()

Activity A:
    onStop()   // if A is no longer visible
```

This is useful to understand when coordinating resources between Activities.

# 18. Best Practices

### `onCreate()`

Use for:

- Initial Activity setup
- UI initialization
- ViewModel setup
- Saved-state restoration

### `onStart()`

Use for:

- Work needed while the Activity is visible
- Starting visibility-dependent resources

### `onResume()`

Use for:

- Foreground-only functionality
- Resuming resources released during `onPause()`

### `onPause()`

Use for:

- Quickly pausing foreground work
- Releasing resources that are unnecessary while paused

Keep it lightweight.

### `onStop()`

Use for:

- Stopping work that is only needed while visible
- Releasing resources
- Appropriate persistence operations

### `onDestroy()`

Use for:

- Final cleanup associated with the Activity instance

Do not use it as the only mechanism for important data persistence.

# 20. Interview Questions

### Q1. What is the Activity lifecycle?

It is the sequence of states and callback methods through which an Android Activity passes from creation to destruction.

### Q2. What is the first lifecycle callback?

`onCreate()`.

### Q3. Which callback means the Activity is visible?

`onStart()`.

### Q4. Which callback means the Activity is in the foreground?

`onResume()`.

### Q5. What is the difference between `onPause()` and `onStop()`?

`onPause()` means the Activity has lost foreground focus and may still be visible. `onStop()` means the Activity is no longer visible.

### Q6. When is `onRestart()` called?

When a previously stopped Activity is about to start again.

### Q7. Can `onDestroy()` happen during screen rotation?

Yes. A configuration change can destroy and recreate the Activity.

### Q8. Should important data only be saved in `onDestroy()`?

No. Use appropriate saved-state, ViewModel, and persistent-storage mechanisms.

### Q9. Why should `onPause()` be lightweight?

The callback is short-lived and may not provide enough time for heavy work such as database transactions or network operations.

### Q10. What is the purpose of a ViewModel?

It stores UI-related state separately from the Activity and can preserve that state across configuration-change recreation.

---

# 21. Key Takeaways

- Activities have a lifecycle controlled by Android.
- The six core callbacks are `onCreate()`, `onStart()`, `onResume()`, `onPause()`, `onStop()`, and `onDestroy()`.
- `onRestart()` is used when a stopped Activity is returning.
- Keep `onPause()` lightweight.
- Use `onStop()` for work that can happen after the Activity becomes invisible.
- Use ViewModel and saved-state mechanisms for appropriate UI state.
- Lifecycle-aware components help keep lifecycle-dependent code organized.
- Modern Compose applications should prefer lifecycle-aware APIs for UI lifecycle handling.
